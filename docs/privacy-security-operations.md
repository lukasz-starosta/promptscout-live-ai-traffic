# Privacy, Security, and Operations Guide

PromptScout Live AI Traffic collectors send request-level analytics events about
AI crawler, AI assistant, and related referral traffic that reached a customer
site. PromptScout receives those analytics events asynchronously. PromptScout is
not in the customer request path unless a customer intentionally self-hosts a
proxy adapter and routes production traffic through that adapter.

## Data Sent to PromptScout

Collectors should send only the canonical event fields documented in
[event-contract.md](event-contract.md):

- schema version, event kind, observation timestamp, and collector provider.
- request host, path, method, and privacy-normalized query string when needed.
- user agent and referer when available for classification.
- provider classification fields generated by the shared classifier.
- optional coarse location fields, such as country or region, when the platform
  already provides them.
- optional integration metadata, such as collector name or platform request ID.
- optional IP hash metadata that describes the hash without storing the raw IP.

Collectors must never send request bodies, response bodies, cookies,
authorization headers, session tokens, customer account identifiers, raw IP
addresses, full request headers, form fields, payment data, or any PromptScout
service role or database credentials.

## Privacy-Safe Defaults

All integrations should default to privacy-safe normalization before delivery:

```ts
await normalizeLiveAiTrafficEvent(event, {
  ip: {
    mode: "hash",
    value: platformIpAddress,
    salt: requiredSecret("PROMPTSCOUT_IP_HASH_SALT"),
    keyId: "site-source-2026-05",
    algorithm: "hmac-sha256",
    truncatedBits: 128,
  },
  query: { mode: "omit" },
  path: { mode: "keep" },
});
```

Use `query: { mode: "allowlist", allow: ["utm_source", "utm_medium"] }` only
when a site owner has explicitly approved those parameters. Use path redaction
for sites that put sensitive values in URL paths, such as
`/accounts/{accountId}` or `/orders/{orderId}`. If an integration cannot
reliably normalize a field, omit it instead of sending a raw value.

## IP Hashing

Raw IP addresses should be discarded after hashing. Prefer HMAC-SHA-256 with a
site-specific salt or secret, and set `originalIpRetention` to
`discarded_after_hash`. Truncating to 128 bits is enough for stable aggregate
analytics while reducing long-term identifiability.

Hash salts are operational secrets. Store them with the same controls as ingest
tokens, rotate them when site ownership changes, and record the active `keyId`
so historical hashes can be interpreted without exposing the salt.

Use `ip: { mode: "omit" }` when a provider, customer policy, or jurisdiction
requires no IP-derived value. Use `ip: { mode: "disabled" }` only to make an
explicit `algorithm: "none"` event for environments that need to prove the IP
was not collected.

## Query Strings and Headers

Query strings are high-risk because applications often place identifiers or
free-text input in them. The default guidance is:

- omit query strings unless analytics requires a small allowlist.
- allowlist marketing tags only when the customer has approved them.
- never forward query keys such as `email`, `token`, `code`, `session`,
  `account`, `user`, `order`, `checkout`, `q`, or `search`.

Collectors may inspect safe source-attribution keys before normalization so the
classifier can detect AI referral visits when browsers omit `Referer`. The
current classifier only uses source-style keys such as `utm_source` and
`source`, and only for known provider values such as `chatgpt.com`, `chatgpt`,
or `chat.openai.com`. This inspection should happen in memory at the collector
boundary; full raw query strings remain omitted before delivery to PromptScout.
For query-classified AI referral visits, the emitted `request.search` may keep
only the closed safe source attribution pair, such as
`?utm_source=chatgpt.com`, so PromptScout can store landing source attribution
without retaining raw landing queries.

Header forwarding must be allowlist-only. The classifier may read headers such
as `user-agent` and `referer`, but collectors must not forward full header
sets. Never send `cookie`, `authorization`, `x-api-key`, `set-cookie`, or
platform-specific secret headers.

PromptScout can count provider/source-level referrals from these parameters. It
cannot identify an individual ChatGPT conversation unless the customer controls
and includes a safe campaign or content identifier in the landing URL, and even
then that identifier should be treated as customer-provided attribution rather
than provider-confirmed conversation metadata.

## Ingest Tokens

PromptScout ingest tokens are scoped to exactly one brand-owned site source.
They are not brand-level credentials, team-wide credentials, or credentials that
can be reused across multiple sites. Rotation and revocation must happen per
site source.

When rotating a token:

1. Create a replacement token for the same site source.
2. Deploy the replacement through that provider's secret storage.
3. Confirm new events are accepted for that site source.
4. Revoke the old token.
5. Remove the old token from provider configuration and deployment history when
   the provider supports secret deletion.

When revoking a token, expect only that site source to stop sending accepted
events. Other sites under the same brand or team must continue to operate with
their own tokens.

## Token Storage by Provider

Do not commit ingest tokens, signing secrets, or IP hash salts to this
repository, example code, customer repositories, Docker images, access logs, or
client-side bundles. Store them in the provider's server-side secret mechanism:

| Provider | Expected storage |
| --- | --- |
| Vercel | Project environment variables for the production/preview environment that runs the middleware. |
| Cloudflare | Worker secrets, not `wrangler.toml` plaintext variables. |
| Netlify | Site environment variables or team-managed secrets available only to server/edge functions. |
| nginx log forwarder | Host secret manager, encrypted deployment variable, or root-readable config outside the web root. |
| WordPress | Server-side WordPress option or environment variable protected from public reads; never browser-visible plugin settings. |
| Node/Express | Server environment variables or deployment secret manager used by the process owner. |
| CloudFront/AWS | AWS Secrets Manager, SSM Parameter Store `SecureString`, or Lambda environment variables encrypted with KMS. |
| Fastly | Fastly Secret Store or protected service variables, not public dictionaries. |

Use separate tokens for production, staging, and development site sources. Never
reuse a production token in local examples.

## Failure Modes

Collectors must fail open for customer traffic. If PromptScout ingest is down,
network requests time out, a provider rate-limits delivery, or a customer origin
returns an error, the collector should not block the page, edge request, or
origin response.

Recommended behavior:

- Vercel, Cloudflare, and Netlify collectors should use their documented
  `waitUntil` lifecycle hooks. Fastly direct-backend delivery is best effort
  because its documented JavaScript `FetchEvent` does not expose `waitUntil`;
  use real-time logging when durable delivery is required. CloudFront delivery
  runs out of band and must fail the Kinesis consumer invocation after retries
  are exhausted so the stream can retry it.
- Node/Express middleware should send in the background after classification and
  must continue the request even when ingest delivery fails.
- nginx log forwarders should spool to the local forwarder/log pipeline and
  preserve the origin response path.
- WordPress collectors should avoid blocking page rendering on ingest delivery.

The ingest client retries retryable HTTP status codes and network failures with
bounded backoff. Each attempt has a two-second default timeout covering the
request and any failure-body read, and successful response bodies are not
buffered. Authentication failures are not retryable
because they usually mean the token was revoked, rotated incorrectly, or
attached to the wrong site source. Provider limits, including `429` responses,
should be retried within the configured budget and then surfaced in provider
logs or monitoring.

## Operational Ownership

The customer owns deployment of the collector in their platform. PromptScout
owns the ingest endpoint, event contract, token issuance/revocation, and
accepted analytics event processing. During incidents, separate customer-path
health from analytics delivery health:

- customer request availability is owned by the customer's hosting/origin path.
- analytics delivery availability is owned by the collector plus PromptScout
  ingest.
- a self-hosted proxy adapter is customer-owned infrastructure and can be in the
  request path only if the customer chose that deployment model.

## Security FAQ

### Does PromptScout proxy customer traffic?

No. Standard collectors observe requests in the customer's platform and send
analytics events to PromptScout out of band. PromptScout is not in the customer
request path unless the customer self-hosts and routes traffic through a proxy
adapter.

### Are ingest tokens brand-level or team-level credentials?

No. Each ingest token is scoped to one brand-owned site source. Rotate and
revoke it per site source.

### What happens when PromptScout ingest is unavailable?

Collectors should fail open, preserve the customer request path, retry within a
bounded budget, and record delivery failures in provider logs or monitoring.
Analytics events may be delayed or dropped, but customer pages should continue
to serve.

### Can collectors send raw IP addresses?

No. Collectors should hash or omit IP addresses before delivery. Raw IP
addresses should be discarded after hashing and should not be stored by the
collector solely for PromptScout analytics.

### Can collectors send cookies or authorization headers?

No. Header handling must be allowlist-only, and cookies, authorization headers,
API keys, and platform secrets must never be sent to PromptScout.

### Can examples include real tokens?

No. Examples must use placeholder environment variable names and privacy-safe
normalization. Never paste real tokens, signing secrets, or hash salts into
documentation, tests, fixtures, screenshots, or support threads.
